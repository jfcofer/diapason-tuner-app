# 0019 — Raise Android minSdk to 28

**Status:** Accepted · 2026-10-09

## Context

Android audio goes through AAudio (`T-002b`). The `oboe` crate, the other candidate, has been
unmaintained since 0.6.1 on 2024-03-03. The maintained binding is the `ndk` crate, which cpal 0.18
also uses on Android.

Its stream builder exposes `input_preset`, `usage` and `content_type` only with the
`api-level-28` feature. Those wrap `AAudioStreamBuilder_setInputPreset` and its siblings, which
Android 9 (API 28) added.

The input preset is the main lever for tuner accuracy (`PLATFORM_AUDIO.md` §2). Without it, Android
applies AGC, noise suppression and a voice-band filter to the microphone, which ruins pitch content.

The pin was `minSdk = 26`. That leaves no clean way to get the preset on API 26–27:

- Bionic's linker binds every imported symbol when the library loads, with no lazy binding. A
  `.so` that imports the API-28 setters therefore fails to load at all on 8.x.
- AAudio on 8.0 is unreliable. Oboe, Google's own wrapper, will not use it there unless forced, and
  logs "This is error prone" when it is (`isAAudioRecommended` requires API 27, O_MR1).

Reach, from StatCounter:

- Worldwide, mobile and tablet, September 2026: Android 11–16 are 91.16% of devices. That puts
  Android 10 and *everything older*, together, at 8.84%. 8.x is a part of that.
- Regional "8.0 Oreo" figures, June–July 2026, are higher: Oceania 4–7%, Germany 5.9%. They are
  noisy month to month.

## Decision

- **`ANDROID_MIN_SDK=28`** in `tools/versions.env`, which `build.gradle.kts` and
  `check-android-release` already read. Nothing else writes the number.
- **`ndk` is used with `api-level-28`.** Every supported device gets the full builder: `Unprocessed`
  where supported, else `VoiceRecognition`, with `usage` and `content_type` set.
- There is no runtime symbol lookup and no OpenSL ES path.

## Consequences

**Good.**
- Every device the app installs on gets the same audio path, and that path can be configured for
  accuracy. A support report never has to ask "which of the three code paths did you take?".
- No `dlsym` or function-pointer `unsafe` in `audio_io`, and no second backend to keep alive.

**Bad.**
- Devices on Android 8.0–8.1 can no longer install the app. That is at most a few percent, mostly
  older budget phones, where AAudio's fast path is rarely granted anyway.
- Already-installed users on 8.x would stop receiving updates. Today that is nobody: the app has
  not shipped.

**Rejected.**
- *Keep 26 and resolve the API-28 setters with `dlsym` at runtime.* It is possible, but it adds
  hand-written `unsafe` function pointers, and on 8.x the tuner would still run with the AGC preset.
  That is a tuner that silently reads wrong, which is worse than one that does not install. On 8.0 it
  would also run on the AAudio version Oboe refuses.
- *Raise to 27 and use `dlsym` for 28.* This drops only 8.0, where AAudio is unreliable. It keeps
  8.1 with the AGC preset and keeps the `dlsym` path, so it pays most of both costs.
- *`oboe` with its OpenSL ES fallback.* OpenSL ES can request an unprocessed source on 26–27, so
  this would keep 8.x with a correct preset. It was rejected anyway: the crate is unmaintained, it
  ships `libc++_shared`, and it means a second native audio API to verify on hardware this project
  does not have.
